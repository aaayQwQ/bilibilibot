# 插件架构整改方案

## 决策摘要

保留当前 C++17 / Qt 6 宿主，不把插件作为原生 C++ DLL/SO 加载。短期继续支持当前 JSON 声明式规则；需要表达复杂流程时，优先把插件编译为 WebAssembly（Wasm），由宿主内嵌运行时执行。Lua 作为备选，不建议作为默认的第三方插件格式。

这里的“稳定”分两层：Wasm 的沙箱和资源限制可以降低插件影响宿主的风险，但不能消除运行时漏洞；若需要强故障隔离，最终应考虑独立受限进程。任何 Wasm/Lua 插件都不应拿到 Bilibili Cookie、CSRF、AI API Key 或任意网络/文件/进程能力。

## 为什么选 Wasm，而不是直接加载 C++ 或 Lua

- **原生 C++ 动态库**：性能好，但与宿主共享地址空间、权限和 ABI。崩溃、越界写或恶意行为都可能直接影响机器人；跨 Windows/Linux/macOS 的 ABI 和依赖也难维护。
- **Lua**：嵌入简单、脚本易写，适合可信的个人自动化。但它运行在宿主进程内；移除标准库并不自动构成安全沙箱，死循环和内存消耗也需要额外治理。若只信任自己编写的脚本，Lua 可以是未来可选适配器，不应被描述成对不可信插件的安全隔离。
- **Wasm**：插件编译成平台无关的模块，默认不应拥有宿主 I/O 能力，宿主可通过窄小、版本化的导入接口授予能力，并设置燃料/执行预算、线性内存上限、输入输出上限和超时。它更符合“第三方功能可扩展，核心凭据不外泄”的目标。

插件作者可用 Rust、C/C++ 等编译到 Wasm；**宿主的安全边界是 Wasm ABI 与运行时配置，而不是作者使用哪种源语言**。运行时选型和构建集成需在实现阶段验证三平台支持、Qt/CMake 集成、许可证、供应链维护和可复现构建；未通过验证前不应合并一个声称已经隔离插件的运行时实现。

## 目标职责边界

### 宿主框架（稳定、最小权限）

1. Bilibili 登录、连接和会话生命周期。
2. 将平台协议事件规范化为版本化事件对象，并接收/发送消息。
3. 提供有限的业务 API（例如申请发送弹幕），所有调用先经过宿主权限策略、限流、长度校验和结果回调。
4. 加载配置、管理插件生命周期、执行资源限制、日志与故障隔离。
5. 提供基础 AI 能力的 API/服务适配器，但 AI 回复策略、触发词、欢迎/礼物感谢等具体功能属于插件。凭据保留在宿主服务中，插件只提交受限请求，不读取密钥。

### 插件

- 订阅声明的事件，执行功能策略，并通过宿主授予的能力请求动作。
- 不直接访问 Qt 对象、网络、文件系统、环境变量、Cookie、配置密钥或任意进程。
- 每个插件拥有单独 ID、版本、API 兼容范围和能力清单；默认无写能力，启用能力需要管理员显式授权。

## 建议的目录与模块边界

```text
src/
  app/                 进程入口、装配、生命周期
  core/                规范化事件、权限策略、动作队列、插件管理接口
  platform/bilibili/   登录、Bilibili 协议、收发消息和平台 API
  services/ai/         受宿主权限控制的 AI 服务适配器
  plugins/json/        现有 JSON 规则解析器与声明式动作
  plugins/wasm/        后续 Wasm 运行时适配器（未实现前不创建可执行伪接口）
  config/              配置读取与凭据处理
tests/
  unit/                解析、权限、限流、序列化和状态机测试
  integration/         mock 平台/API 的端到端测试
docs/
  PLUGIN_API.md        当前稳定的声明式 API
  PLUGIN_ARCHITECTURE.md 本架构与迁移计划
```

这是目标结构，不意味着本次提交已经移动源码。当前 `src/main.cpp` 同时承载装配、AI 触发队列、冷却、历史、日志和回显去重；`src/bilibili.cpp` 把登录、协议解析、事件规范化和发送队列合在 `BilibiliClient`；`src/plugin_api.cpp` 只实现 JSON 规则，并非任意脚本插件运行时。后续按小步提取，确保每一步都有回归测试，不应先做大规模目录搬迁再补测试。

## Wasm 插件协议草案

先将协议定义成与 Qt/C++ 类型无关的 JSON 消息，便于测试、版本协商以及未来必要时迁移到独立进程：

- 宿主向插件传递一个规范化事件；插件只在明确订阅的事件类型上被调用。
- 插件返回零个或多个受限动作请求。第一阶段仅考虑 `send_danmaku`；动作请求仍由宿主统一校验与排队。
- 每个调用使用独立输入/输出缓冲区；定义最大事件字节数、最大输出字节数、最大动作数、执行燃料/指令预算、线性内存上限与单次调用超时。
- 插件初始化和每次事件处理都有明确结果码；trap、超时、超限或无效输出均拒绝该次动作，记录插件 ID 和原因，并允许宿主继续工作。
- ABI 必须显式携带 `api_version`、插件 ID/版本、订阅事件和所需能力；未知版本、未知字段策略和升级/降级行为需要文档化。
- 不向模块导入 WASI 文件、网络、环境变量或任意时钟接口。若未来确有需要，按能力逐项设计并默认拒绝。
- 不允许插件直接调用 Bilibili/AI 网络 API；由宿主服务持有凭据并执行允许的操作。

JSON 是边界格式而不是信任机制。所有字段仍须做大小、类型、数值范围、Unicode 和动作授权校验；插件输出不能因其来自 Wasm 而绕过现有 `PluginManager` 的限制。

## 建议迁移顺序

1. **守住现状**：继续让 JSON 插件默认关闭；原有 64 KiB 清单、32 个插件、180 字弹幕、符号链接拒绝、显式发送权限保持不变。不要在同一版本移除已有格式。
2. **提取纯接口**：定义平台无关的 `NormalizedEvent`、`ActionRequest`、`PluginDescriptor`、能力集合和结果类型；用单元测试锁定现有 JSON 行为。
3. **收敛宿主入口**：把 `main.cpp` 的 AI 自动回复流程抽成宿主服务/插件策略，将 `main()` 变成构造和连接依赖的薄入口。平台客户端只负责认证、事件传递与消息发送，不决定何时回复。
4. **先验证运行时**：为候选 Wasm runtime 建立独立原型和 CI 矩阵；验证无 WASI 导入、燃料耗尽可恢复、内存/输入输出上限有效、插件 trap 不使宿主退出，以及 Windows/Linux/macOS 构建和许可证。
5. **限权执行**：将 Wasm 适配器接入统一动作策略；默认不授权任何写动作，按插件 ID 和能力逐项许可，发送动作复用现有有界队列和速率限制。
6. **灰度上线**：先只读事件插件，再开放 opt-in 的发送动作；保留关闭 Wasm 功能的开关、诊断日志、兼容性测试和旧 JSON 插件回退。

## 当前代码审查中应优先整改的事项

### P0：先补测试与故障路径

- **`src/main.cpp` 过重**：AI 自动回复是业务功能但直接放在入口；队列、用户/房间冷却、历史、发送确认和回显去重交织，增加模块化前应先抽取并为边界行为加测试。
- **测试目前不覆盖完整 AI 网络流程**：`AIClient` 直接使用真实 `QNetworkAccessManager`，应注入传输接口或提供本地 HTTPS mock，覆盖超时、取消、错误响应、超大响应、JSON 解析失败和停止时回调。
- **平台请求响应大小限制不一致**：AI 与发送弹幕响应有显式流式上限，但 `BilibiliClient::requestJson()` 只限制 read buffer，并在完成时 `readAll()`，缺少明确的累计响应上限。应像其他网络请求一样流式累计、超限取消，并增加回归测试。
- **配置加载会在校验前写权限**：`Config::load()` 在解析/验证成功之前尝试修改 config 与 Cookie 权限。考虑先用只读方式验证路径/内容，再限制权限；记录权限失败并保持明确的安全提示。Windows ACL 的边界在 CHANGELOG 已注明。
- **插件异步回调生命周期**：`PluginManager::dispatch()` 传出的完成回调捕获 `this`。应明确 manager 停止/销毁时如何取消或使回调失效，并测试延迟完成、重复完成、关停竞态；异步回调必须不能访问已销毁 manager。

### P1：提高模块可维护性

- 将 `BilibiliClient` 拆成认证/API、WebSocket 会话、协议编解码、事件规范化和发送队列等可独立测试组件；不要让插件看到平台原始 JSON。
- 将配置按 `BilibiliConfig`、`AiConfig`、`BotConfig`、`PluginConfig`、`LoggingConfig` 分组，避免一个全局 `Config` 暴露 Cookie 与 AI Key 给不需要它的业务层。
- 把权限控制从 `PluginManager` 的单个 `enabled/allowSendDanmaku` 布尔量发展为宿主拥有的能力策略；所有插件动作统一过该策略，不让插件实现自行判定授权。
- 对每条规范化事件定义 schema 和版本；为非数值 JSON 字段、未知事件、乱序/重复事件、超长用户文本和事件风暴增加测试/限流。
- 加入本地 mock 集成测试和 CI 的跨平台测试；目前工作流有 Qt Test 与 Linux ASan/UBSan，但真实网络/凭据交互应由 mock 验证，而不是依赖直播间。

### P2：维护性与发布

- `CMakeLists.txt` 目前把所有生产代码直接编译进一个 executable；拆出 `core`、`platform_bilibili`、`services_ai`、`plugins_json` 库/目标，保持可测试依赖方向。
- 检查并清理 `src/bilibili.hpp` 中重复的 `<functional>` include。
- 测试拆分为 unit/integration，并确保 Release 工作流等待的 CI 工作流会在目标分支及触发方式下实际运行；当前 release 工作流依赖同一 SHA 上的 Build and Test 与 CodeQL 结果，需持续验证触发条件没有分支配置漂移。
- 文档要明确区分“当前已实现的 JSON 声明式插件”与“规划中的 Wasm 插件”，在运行时、权限和隔离通过测试前不要暗示脚本/Wasm 已可加载或已受沙箱保护。

## 本次状态

本文件定义目标边界和整改顺序。当前仓库只实现 JSON 声明式插件；尚未加入 Lua/Wasm 引擎，也未将现有功能改成脚本插件。Wasm runtime 的选择、三平台构建验证和代码迁移需要单独实现与测试，不应把设计方案误当成可运行功能。
